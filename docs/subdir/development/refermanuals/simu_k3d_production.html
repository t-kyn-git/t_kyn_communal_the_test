### EKSで利用できる共有ボリュームの選定 EKSの複数Podから同時に読み書きできる共有ボリューム (ReadWriteMany: RWX) が必要な場合、AWSでは **Amazon EFS (Elastic File System)** が最も一般的で親和性の高い選択肢となります。 #### Amazon EFSとは？ * フルマネージドのNFSファイルシステムサービスです。 * 複数のEKSワーカーノード（EC2インスタンス）から同時にマウントして利用できます。 * 保存容量に応じて自動的にスケールするため、事前に容量をプロビジョニングする必要がありません。 * `EFS CSI (Container Storage Interface) driver` をEKSクラスターにインストールすることで、Kubernetesネイティブな方法（`PersistentVolume`, `PersistentVolumeClaim`）で簡単に利用できます。 #### ユースケース * ユーザーがアップロードした画像やファイルなどの共有ストレージ * 複数Podで共有する設定ファイルやデータの置き場 * CMS（Contents Management System）のコンテンツ置き場 --- ### 料金見積もりへの追加 これを踏まえ、以前の料金概算にAmazon EFSのコストを追加します。 **シナリオ:** ユーザーがアップロードしたファイルなどが蓄積され、**合計1TBのストレージ**が必要になり、ピーク時に**100MB/sのスループット**を確保するケースを想定します。 | コンポーネント | 料金 (USD) | 料金 (JPY) | 備考 | | :--- | :--- | :--- | :--- | | **ストレージ料金** | ~$95 | ~¥14,250 | ライフサイクル管理を有効化し、80%が低頻度アクセス(IA)に移動したと仮定 | | **スループット料金** | ~$343 | ~¥51,450 | プロビジョニングドスループット (100MB/s) を確保した場合。バーストモードでは変動。| | **バックアップ料金** | ~$62 | ~¥9,300 | AWS Backupを利用した場合 (本番では必須) | | **EFS合計** | **~$499** | **~¥75,000** | | --- ### 全体を統合した最終版マークダウン 以下に、EFSの共有ボリュームに関する記述と見積もりを反映した、最終版のマークダウンを提示します。 # 100万人規模のサービスを支えるKubernetes (EKS) 構成案：設計からコスト、チーム体制まで ## 0. 現状の構成 (k3d on GitHub Codespaces) と大規模化への課題 まず、現在の小規模な検証環境について整理します。この構成から100万人規模の本番環境へ移行するにあたり、解決すべき課題を明確にします。 ### 0.1. 現状の構成概要 * **環境:** GitHub Codespaces 上のシングルk3dクラスタ * **リソース:** メモリ 5GB、CPU 2コアの範囲で稼働 * **ワークロード:** * **アプリケーション:** Python (Deployment), Nginx (Deployment) * **データベース:** MySQL (Pod/Deployment) * **監視スタック:** * Prometheus (Deployment) * Grafana (Deployment) * 各種Exporter (node, process, nginx, python, mysql) * **ロギングスタック:** * Fluentd-server (Deployment) * Fluentd-agent (DaemonSet) * **対象ユーザー:** 家族のみ（数人規模） ### 0.2. 大規模化に向けた課題 この構成は学習や小規模なテストには非常に有効ですが、本番環境として100万人のユーザーを支えるには、以下のような根本的な課題が存在します。 * **スケーラビリティの欠如:** シングルノードのk3d環境では、トラフィックの急増に対応できません。Podやノードの自動的なスケールアウトが困難です。 * **可用性の問題:** GitHub Codespacesは開発環境であり、24時間365日の稼働を保証していません。また、構成全体が単一障害点（SPOF）の塊であり、何かが停止するとサービス全体がダウンします。 * **データ永続性のリスク:** k3d内でデータベースを運用することや、Podが停止するとファイルが消えることは、データ消失のリスクが非常に高いです。適切なバックアップ、リストア、フェイルオーバーの仕組みが存在しません。 * **運用性の限界:** 手動での運用が前提となり、CI/CDパイプラインや自動化された監視・アラート体制が不十分で、大規模サービスの運用には耐えられません。 --- ## 1. クラウド構成案と基本方針 これらの課題を解決し、100万人規模のトラフィックに対応するため、以下のようなクラウド構成を提案します。 ### 1.1. 基本方針 * **マネージドKubernetesの採用:** Amazon EKS (Elastic Kubernetes Service) を採用し、コントロールプレーンの運用管理をAWSに任せます。 * **マネージドデータベースの採用:** MySQLはAmazon RDS for MySQLを利用します。 * **共有ファイルストレージの採用:** 複数のPodでファイルを共有するために、Amazon EFS (Elastic File System) を利用します。 * **各コンポーネントに適したクラウドサービスの活用:** ログはAmazon CloudWatch、メトリクスはAmazon Managed Service for Prometheus (AMP) といったクラウドネイティブなサービスを組み合わせます。 ### 1.2. 推奨アーキテクチャ概要 ``` (インターネット) | [AWS Application Load Balancer] (L7/HTTP(S)) <--- (SSL終端) | [Ingress Controller (Nginx)] | +-------------------------------------------------------------------------+ | [Amazon EKS Cluster] | | | | --- ワーカーノードプール (アプリケーション) --- | | | Pod (Python App) | <=> | Pod (Python App) | ... (HPA & Karpenter) | | ------------------------------------------- | | ^ | | | (ReadWriteMany) | | v | | --- [Amazon EFS] (共有ファイルストレージ) --- | | | | --- (その他ノードプール: 監視、汎用...) --- | +-------------------------------------------------------------------------+ | | | | (Metrics) | (Logs) | (DB Connection) v v v [Amazon Managed [Amazon CloudWatch Logs] [Amazon RDS for MySQL] Service for Prometheus] ``` ## 2. EKSワーカーノードの必要数 ### 2.1. 最低ノード数：3台 本番環境として最低限の可用性を担保するため、AZ障害に耐えられるよう、**最低3台のワーカーノード**を異なるAZに分散して配置することを推奨します。 ### 2.2. 最大ノード数の想定：数十台〜100台超 試算の結果、最大ノード数は**平常時のピークで数十台、大規模イベント時には100台を超える規模**を想定します。重要なのは、**Karpenter**等のツールで負荷に応じてノード数をリアルタイムに自動増減させる仕組みです。 ## 3. インスタンススペックと料金概算 * **前提:** 東京リージョン、オンデマンド料金、1ドル=150円、月730時間稼働で計算。 ### 3.1. 最小構成 (サービス開始時のベースライン / 合計7台) | コンポーネント | スペック / 内容 | 月額料金 (USD) | 月額料金 (JPY) | | :--- | :--- | :--- | :--- | | **EKS Control Plane** | 1クラスター | ~$73 | ~¥10,950 | | **Worker Nodes (EC2)** | `m6g.xlarge` × 3台, `r6g.xlarge` × 2台, `t4g.large` × 2台 | ~$754 | ~¥113,100 | | **ストレージ (EBS)** | 100GB/node (gp3) × 7台 | ~$65 | ~¥9,750 | | **共有ボリューム (EFS)** | 数GB利用・バーストスループット | ~$10 | ~¥1,500 | | **ロードバランサー (ALB)** | 1台 (小トラフィック) | ~$30 | ~¥4,500 | | **データ転送** | NAT Gateway + Egress (例: 1TB) | ~$150 | ~¥22,500 | | **マネージドDB (RDS)** | `db.t4g.large` Multi-AZ | ~$170 | ~¥25,500 | | **合計** | | **~$1,252** | **~¥187,800** | > **最小構成での月額料金（目安）: 約18.8万円** ### 3.2. 最大負荷構成 (ピーク時の参考 / 合計65台) | コンポーネント | スペック / 内容 | 月額料金 (USD) | 月額料金 (JPY) | | :--- | :--- | :--- | :--- | | **EKS Control Plane** | 1クラスター | ~$73 | ~¥10,950 | | **Worker Nodes (EC2)** | `m6g.xlarge` × 50台, `r6g.xlarge` × 5台, `t4g.large` × 10台 | ~$7,155 | ~¥1,073,250 | | **ストレージ (EBS)** | 100GB/node (gp3) × 65台 | ~$600 | ~¥90,000 | | **共有ボリューム (EFS)** | 1TB, 100MB/sスループット, バックアップ込 | ~$499 | ~¥75,000 | | **ロードバランサー (ALB)** | 1台 (高トラフィック) | ~$200 | ~¥30,000 | | **データ転送** | NAT Gateway + Egress (例: 20TB) | ~$2,000 | ~¥300,000 | | **マネージドDB (RDS)** | `db.m6g.xlarge` Multi-AZにスケールアップ | ~$400 | ~¥60,000 | | **合計** | | **~$10,927** | **~¥1,639,200** | > **最大負荷で24時間稼働し続けた場合の月額料金（参考）: 約164万円** ### 3.3. 料金を最適化するためのポイント 1. **Savings Plans / リザーブドインスタンスの活用:** 常時稼働するノードに適用し、**最大40%〜60%の割引**を目指します。 2. **スポットインスタンスの活用:** オートスケールで増減するノードに活用し、**最大90%のコスト削減**を目指します。 3. **ストレージのライフサイクル管理:** EFSやS3のライフサイクルポリシーを活用し、アクセス頻度の低いデータを安価なストレージクラスに自動で移動させます。 ### 3.4. (補足) 共有ストレージの代替案：Amazon S3 ユーザーがアップロードしたファイルを保存・配信する用途の場合、**Amazon S3** を利用するのが現在のベストプラクティスです。 * **メリット:** EFSよりもさらに高い耐久性とスケーラビリティ、そして圧倒的に安価なストレージコスト。 * **デメリット:** ファイルシステムとして直接マウントできないため、アプリケーション側でAWS SDKを使い、S3へファイルをアップロード/ダウンロードする実装への改修が必要になります。 既存のアプリケーションがファイルシステムへの読み書きを前提としている場合はEFSが、新規開発や改修が可能であればS3の採用を強く推奨します。 ## 4. 必要なチーム体制と人件費（工数） ### 4.1. 初期構築フェーズ (3ヶ月〜1年超) チームの習熟度にもよりますが、多くの場合 **5名チームで半年以上、合計30人月以上の工数を見込む** のが現実的な計画です。 ### 4.2. 運用・改善フェーズ (継続) サービスの安定稼働と成長のため、**SREチーム(2〜3名)とアプリケーション開発チーム(2〜4名)を含む、最低でも5名〜8名程度のエンジニアリングチーム**が継続的に必要になります。健全なオンコール体制を組むには、SREは最低3名いることが望ましいです。 ### 4.3. 人件費に関する考察 * **人件費は最大の「投資」:** モダンなインフラを構築・運用できるエンジニアへの投資が、将来の運用コストを大幅に削減します。 * **マネージドサービスの活用は人件費削減に繋がる:** RDSやEFS、AMPなどを積極的に採用することで、SREチームの運用負荷を下げ、より生産的な業務に集中させることができます。 * **自動化への投資:** 初期構築でIaCやCI/CDを徹底することが、長期的な運用コストを抑制します。 ---
